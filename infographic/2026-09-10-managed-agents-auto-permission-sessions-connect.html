Claude Managed Agents に auto 権限ポリシーが追加
ant CLI にセッション接続コマンドが登場

📅 2026-09-10 | ソース: Claude Developer Platform Release Notes

auto 権限ポリシー evaluation フィールド ant beta:sessions connect --web オプション

概要 — キーポイント

🛡️

auto 権限ポリシーの追加

Managed Agents の権限ポリシーに auto が追加された。サーバーがエージェントツールおよび MCP ツールの各呼び出しを評価し、実行・拒否・承認待機のいずれかを判断する。always_allow の利便性と always_ask の安全性の中間に位置する選択肢。

📊

evaluation フィールドで結果を透明に報告

評価結果は agent.tool_use および agent.mcp_tool_use イベントの evaluation フィールドで、evaluated_permission とあわせて報告される。auto の場合は reason_code も記録され、監査や分岐処理に活用できる。

⌨️

ant beta:sessions connect コマンド

ターミナルを Managed Agents セッションに接続し、トランスクリプトのライブ追跡、メッセージ送信、承認待ちツール呼び出しの許可 / 拒否が行える。Ctrl+C でデタッチしてもセッションは動作し続ける。

🌐

--web オプションでブラウザ操作

--web を付けると、Claude Console のセッションビューアを 127.0.0.1 のローカルサーバーとして起動し、ブラウザからセッションを操作できる。認証情報は CLI の外に出ない。

⚠️

auto は人間によるチェックポイントではない

サーバーが安全と判断した呼び出しは誰の目にも触れる前に実行され、その影響は取り消せない場合がある。実行前に人間のレビューが必須のツールには引き続き always_ask を設定する必要がある。

背景 — 2 択だった権限ポリシーの中間解

Managed Agents では、サーバー実行型のツール (事前構築されたエージェントツールセットと MCP ツールセット) の実行を権限ポリシーで制御する。これまでのポリシーは always_allow と always_ask の 2 種類のみで、デフォルトはエージェントツールセットが always_allow、MCP ツールセットが always_ask だった。

Before — 2 択の権限ポリシー

always_allow は承認の手間がない一方でリスクの高い呼び出しも素通りし、always_ask は安全な呼び出しにも毎回承認が必要だった。承認待ちへの応答も、API で user.tool_confirmation イベントを送信するか Console を使用する必要があった。

After — auto とターミナル接続

auto によりサーバーが呼び出しごとにコンテキストを考慮して実行可否を判断できるようになった。あわせて ant beta:sessions connect により、ターミナルやローカルブラウザから対話的に承認待ちへ応答できるようになった。

主要機能

🛡️ auto 権限ポリシー

サーバーがツールの種類、呼び出しの入力、そこまでのセッション内容を考慮して評価するため、同じツールへの 2 つの呼び出しでも異なる判断になり得る。permission_policy に {"type": "auto"} を設定して有効化し、default_config と configs の両方で指定できる。デフォルトで auto になるツールセットはない。

📊 evaluation フィールド

agent.tool_use / agent.mcp_tool_use イベントに、結果を生んだポリシーを示す evaluation オブジェクトが含まれるようになった。auto の場合はサーバーの判断内容と、結果が ask または deny のときの reason_code も記録される。

⌨️ ant beta:sessions connect

ターミナルを既存の Managed Agents セッションに接続。トランスクリプトのライブ追跡、メッセージ送信 (user.message)、エージェントの中断 (user.interrupt)、承認待ちへの Yes / No / 理由付きの No での応答が可能。再接続すると全履歴が読み込まれる。

🌐 --web オプション

Console のセッションビューアを 127.0.0.1 のローカルサーバーとして起動し、ブラウザからメッセージ送信、中断、許可 / 拒否が行える。ターミナルビューと異なり、マルチエージェントセッションのすべてのスレッドを追跡する。URL は表示から 2 分以内に 1 回だけ開ける。

🚫 覆せない拒否

auto でサーバーが高リスクと評価した呼び出しは実行されず、エージェントは is_error: true のエラーツール結果を受け取る。セッションは継続するが、クライアントはこの拒否を覆せない。拒否済みの呼び出しに user.tool_confirmation を送ると 400 エラーになる。

3 つの権限ポリシー

✅ always_allow

確認なしでツールを自動実行する。エージェントツールセットのデフォルト。

自動実行

⏸️ always_ask

セッションを一時停止し、承認を待ってから実行する。MCP ツールセットのデフォルト。

毎回承認

🛡️ auto (新規)

サーバーが各呼び出しを評価し、実行・拒否・承認待機を判断する。

サーバー評価

🔀 auto の 3 つの評価結果

  • 実行: サーバーが安全と判断した場合、always_allow と同様にツールが実行される
  • 拒否: サーバーが高リスクと評価した場合、ツールは実行されない。エージェントは is_error: true のエラーツール結果を受け取り、セッションは継続する。クライアントはこの拒否を覆せない
  • 承認待機: サーバーが判断を下せない場合、always_ask と同様にセッションが一時停止し、ユーザーの承認を待つ

技術詳細

📊 evaluation フィールドの組み合わせ

evaluation オブジェクトとトップレベルの evaluated_permission ("allow"、"ask"、"deny" のいずれか) の対応関係は以下のとおり。reason_code はクライアントの分岐処理や監査記録に使う値であり、エンドユーザーに表示するテキストではない。

evaluation evaluated_permission 意味
{"type": "always_allow"} "allow" ポリシーが always_allow のため実行された
{"type": "always_ask"} "ask" ポリシーが always_ask のため承認待ちになった
auto + {"type": "allow"} "allow" auto でサーバーが安全と判断し実行された
auto + ask / indeterminate "ask" auto でサーバーが判断を下せず承認待ちになった
auto + deny / high_risk "deny" auto でサーバーが高リスクと評価し拒否した

セッションで有効化されていないツールが呼ばれた場合や、evaluation 導入前に記録されたイベントでは、evaluation フィールドは含まれない。

⌨️ sessions connect の主なキー操作

キー 動作
Enter 入力を user.message イベントとして送信 (Alt+Enter または Ctrl+J で改行)
Esc 実行中のエージェントを中断
Ctrl+O 詳細表示の切り替え (ツールの入出力、トークン使用量、ステータスイベント)
Page Up / Page Down トランスクリプトのスクロール
Ctrl+C デタッチ (セッションは動作し続ける)

🧭 auto における意図の扱い

user.message はユーザーの意図と見なされる

user.message イベントで投稿した内容はユーザーの意図と見なされ、本来拒否される呼び出しが許可される可能性がある。一方、ツール結果、取得した Web ページ、MCP サーバーの応答、セッションスレッド間のメッセージからは意図を読み取らない。サーバーはこれらのコンテンツを評価するが、指示としては受け取らない。

⚠️ auto は人間によるチェックポイントではない

サーバーが安全と判断した呼び出しは誰の目にも触れる前に実行され、その影響は取り消せない場合がある。信頼できないエンドユーザーの入力を user.message として中継すると、その入力もユーザーの意図として解釈される。実行前に人間のレビューが必須のツールには always_ask を設定すること。

ベータヘッダーとカスタムツール

Managed Agents API リクエストにはベータヘッダー managed-agents-2026-04-01 が必要 (メモリストアエンドポイントは agent-memory-2026-07-22)。SDK は適切なベータヘッダーを自動的に設定する。カスタムツールはアプリケーション側で実行されるため、権限ポリシーの対象外。

コード例

エージェントツールセットと GitHub MCP ツールセットのデフォルトを auto にし、bash のみ always_ask に上書きする例。

Python auto ポリシーの設定例 
agent = client.beta.agents.create(
    name="Ops Agent",
    model="claude-opus-5",
    mcp_servers=[
        {"type": "url", "name": "github", "url": "https://mcp.example.com/github"},
    ],
    tools=[
        {
            "type": "agent_toolset_20260401",
            "default_config": {
                "permission_policy": {"type": "auto"},
            },
            "configs": [
                {"name": "bash", "permission_policy": {"type": "always_ask"}},
            ],
        },
        {
            "type": "mcp_toolset",
            "mcp_server_name": "github",
            "default_config": {
                "permission_policy": {"type": "auto"},
            },
        },
    ],
)

開発者への影響

🎯 対象

  • Managed Agents でエージェントを構築している開発者
  • MCP サーバーをエージェントに接続している開発者
  • セッションイベントを処理するクライアントを実装している開発者
  • ant CLI でエージェントの運用・デバッグを行う開発者

🛠️ 必要なアクション

  • auto の採用検討: always_allow ではリスクが高く、always_ask では承認負荷が大きいツールについて auto の採用を検討する。人間のレビューが必須のツールには引き続き always_ask を設定する
  • イベント処理の更新: クライアントが未知の evaluation.type や reason_code を許容するように実装する。evaluation フィールドが存在しないイベントにも対応する
  • 監査ログの活用: evaluation フィールドと reason_code を監査記録に保存し、拒否時の分岐処理に利用する
  • 拒否の扱い: auto でサーバーが拒否した呼び出しに user.tool_confirmation を送ると 400 エラーになる。クライアントは拒否を覆せない点を考慮する
  • CLI の更新: ant beta:sessions connect を使用するには CLI を最新版に更新する。スクリプトでは対話型のこのコマンドではなく、ant beta:sessions:events stream と ant beta:sessions:events send を使用する

ユースケース

🛡️ 承認負荷とリスクのバランスを取った権限設計

ファイル操作やコマンド実行など、always_allow ではリスクが高く always_ask では承認負荷が大きいツールに auto を設定する。サーバーがツールの種類、入力、セッション内容を考慮して呼び出しごとに判断するため、安全な呼び出しは自動実行しつつ、高リスクな呼び出しは拒否または承認待機にできる。破壊的な操作が必須レビュー対象なら bash のみ always_ask に上書きする、といった細かな制御も可能。

⌨️ ターミナルからのエージェント運用・デバッグ

長時間動作する Managed Agents セッションに ant beta:sessions connect で接続し、トランスクリプトをライブで追跡しながら、承認待ちのツール呼び出しに Yes / No / 理由付きの No で即座に応答する。Ctrl+C でデタッチしてもセッションは動作し続け、再接続すれば全履歴を確認できるため、常時監視は不要。

📊 evaluation フィールドを使った監査とコンプライアンス

すべてのツール呼び出しイベントの evaluation オブジェクトと reason_code を監査ログに保存し、どのポリシーがどの判断を下したかを追跡する。auto による拒否 (high_risk) の頻度を分析してポリシー設定を見直したり、拒否時にクライアント側で代替フローへ分岐したりできる。

まとめ

⚖️

利便性と安全性の中間となる auto ポリシー

auto 権限ポリシーにより、always_allow の利便性と always_ask の安全性の中間となる選択肢が提供され、サーバーが呼び出しごとにコンテキストを考慮して実行可否を判断できるようになった。評価結果は evaluation フィールドで透明に報告され、監査や分岐処理に活用できる。ただし auto は人間によるチェックポイントの代替ではなく、レビューが必須のツールには always_ask を設定する必要がある。

🚀

エージェント運用ワークフローの大幅な改善

あわせて追加された ant beta:sessions connect により、ターミナルやローカルブラウザからセッションをライブで追跡し、承認待ちの呼び出しに即座に応答できるようになった。Managed Agents の権限制御と運用性を強化するアップデートである。
