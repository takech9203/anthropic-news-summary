API / SDK 認証・セキュリティ

🔑 Console の個人キー / サービスアカウントキー対応と SDK beta 名前空間の GA 形式移行

📅 2026-08-27 | Claude Platform Release Notes

Files / Skills API の GA 化の総仕上げと、「キーが所有者より長生きしない」API キー管理のモダナイゼーション。2 つの重要な更新が発表されました。

📌 概要

📦

SDK の beta 名前空間が GA 形式に移行

Python 1.2.0、TypeScript 0.122.0、Go 1.68.0、Java 2.59.0、Ruby 1.67.0、C# 12.44.0 以降、client.beta.files と client.beta.skills は files-api-2025-04-14 / skills-2025-10-02 beta ヘッダーを送信せず、GA 版と同じレスポンス形式を返します。

👤

Console で個人キー / サービスアカウントキーを作成可能に

Claude Console の Settings → API keys で、ユーザーまたはサービスアカウントという「アイデンティティ」に紐付くキーを作成できるようになりました。

🚫

キーが所有者より長生きしない

リンクされたアカウントが組織から削除されると、キーは自動的に動作を停止します。退職者のキーが残り続けるリスクが解消されます。

📊

アカウントごとの使用状況の追跡が容易に

すべてのリクエストがアイデンティティとして動作するため、組織管理者はアカウント単位で API 使用状況を追跡しやすくなります。

🗂️

既存統合への影響は限定的

beta ヘッダーを明示的に送信し続けるリクエストは従来形式を維持し、従来のワークスペース API キーもレガシーオプションとして引き続きサポートされます。

🔄 Before / After

📦 SDK の Files / Skills アクセス

Before

  • client.beta.files / client.beta.skills が beta ヘッダーを自動送信
  • beta 形式のレスポンス (has_more / first_id / last_id ページネーション)
  • beta と GA でレスポンス形式の二重管理が必要

After

  • beta ヘッダーは送信されず、GA 版の client.files / client.skills と同じレスポンス形式
  • page / next_page カーソルによる一貫したページネーション
  • beta ヘッダーを明示送信すれば従来形式を維持可能

🔑 API キーの管理

Before

  • ワークスペース API キーは「誰のものでもない」キー
  • 作成者が組織を離れても動作し続ける
  • キーの所有者と実際の利用者の対応関係が不明瞭

After

  • すべての API キーを組織が管理するアイデンティティに紐付け可能
  • アカウントの削除でキーは自動的に無効化
  • アカウントごとの使用状況を追跡しやすい

✨ 主な機能

👤 個人キー

作成したユーザー本人として動作し、そのロールと権限を持ちます。ユーザーが組織またはワークスペースへのアクセスを失うと無効になり、組織から削除されるとキーはアーカイブされます。自身の開発・スクリプト向けです。

🤖 サービスアカウントキー

サービスアカウントとして動作し、CI や本番サービスなどの共有・無人ワークロード向けです。サービスアカウントがアーカイブされる、または対象ワークスペースから削除されると無効になります。

📦 SDK beta 名前空間の統合

6 言語の SDK で client.beta.files / client.beta.skills が GA 形式に統一されました。beta 名前空間は Managed Agents beta の scope_id フィルタリングなど、beta 段階の機能向けの betas 引数を引き続き受け付けます。

🎯 キーのスコープ選択

特定のワークスペースにスコープするか、管理エンドポイント (Admin API) およびアクセス可能な全ワークスペースで動作させるかを、キー作成時に選択できます。

⏰ 有効期限とメール通知

プリセット (3 時間、1 日、7 日、30 日)、カスタム期間、「Never」から選択可能です。組織に最大有効期限ポリシーがある場合は「Never」は選択できず、期限が近づくと作成者にメール通知が送信されます。

🗝️ API キーの種類の比較

キーの種類は以下の 3 つに整理されます。個人キーとサービスアカウントキーは「アイデンティティ紐付き (identity-backed)」です。

キーの種類 動作主体 有効範囲 無効になる条件
👤 個人キー 作成したユーザー本人 (そのロールと権限) 単一ワークスペース、またはロールが API 利用を許可する全ワークスペース ユーザーが組織またはワークスペースへのアクセスを失ったとき。組織から削除されるとキーはアーカイブ
🤖 サービスアカウントキー サービスアカウント 単一ワークスペース、またはサービスアカウントがアクセスできる範囲 サービスアカウントがアーカイブされる、または対象ワークスペースから削除されたとき
🗂️ ワークスペースキー (レガシー) なし (ワークスペース所属) 作成されたワークスペースのみ 期限切れ、無効化・削除、ワークスペースのアーカイブ
💡 アイデンティティ紐付きキーの特徴 すべてのリクエストがそのアイデンティティとして動作し、同じ権限を持ちます。リンクされたアカウントが組織から削除されるとキーは自動的に動作を停止し、組織管理者はアカウントごとの API 使用状況を追跡しやすくなります。

⚙️ 技術詳細

📦 対象 SDK バージョン一覧

以下のバージョン以降で、client.beta.files / client.beta.skills が GA 形式に統合されます。

🐍 Python 1.2.0 🟦 TypeScript 0.122.0 🐹 Go 1.68.0 ☕ Java 2.59.0 💎 Ruby 1.67.0 🎼 C# 12.44.0

🔀 SDK 更新後の変更点

  • client.beta.files と client.beta.skills は files-api-2025-04-14 / skills-2025-10-02 beta ヘッダーを送信しない
  • レスポンスは client.files / client.skills と同じ GA 形式 (型名には Beta プレフィックスが付く)
  • client.beta.skills.delete() は Skill を全バージョンごと削除する (GA 版の仕様に統一)
  • beta Messages 型 BetaSkill は BetaContainerSkill にリネーム
  • beta 名前空間は beta 段階の機能向けの betas 引数を引き続き受け付ける
💡 既存統合への影響 beta ヘッダーを明示的に送信し続けるリクエストは従来の beta 形式のレスポンスを維持するため、既存の統合は変更を加えるまで動作し続けます。

📁 Files API の beta 形式と GA 形式の違い

項目 files-api-2025-04-14 あり ヘッダーなし (GA 形式)
List レスポンス { data, has_more, first_id, last_id } { data, next_page } (next_page を page クエリパラメータに渡す)
List カーソル before_id、after_id page、または最大 100 件の ids[] (before_id / after_id は 400 エラー)
ファイルオブジェクトの expires_at 返されない 常に存在 (有効期限なしの場合は null)
アップロード時の Content-Type 必須 省略可能 (省略時は自動検出)

🌐 ワークスペースの選択

  • ワークスペースにスコープされていない個人キー / サービスアカウントキーでは、anthropic-workspace-id ヘッダーで対象ワークスペースの ID を指定する
  • ヘッダーを省略すると 400 invalid_request_error が返される
  • 特定のワークスペースにスコープしたキーではこのヘッダーは不要
  • Admin API は、ワークスペースにスコープされていない個人キーまたはサービスアカウントキーのみを受け付ける

⏰ キーの有効期限

  • プリセット (3 時間、1 日、7 日、30 日)、カスタム期間、または「Never」から選択可能
  • 組織に最大有効期限ポリシーがある場合は「Never」は選択できない
  • 有効期限が近づくと、キーの作成者にメール通知が送信される

💻 コード例

Python Python SDK 1.2.0 以降: GA 形式の Files / Skills API 
# Python SDK 1.2.0 以降: GA 形式の Files / Skills API
from anthropic import Anthropic

client = Anthropic()  # ANTHROPIC_API_KEY を読み込む

# GA 名前空間を使用 (beta ヘッダーは不要)
files = client.files.list()

# ワークスペースにスコープされていない個人キー / サービスアカウントキーの場合、
# anthropic-workspace-id ヘッダーが必須
workspace_client = Anthropic(
    default_headers={"anthropic-workspace-id": "wrkspc_01JwQvzr7rXLA5AGx3HKfFUJ"},
)

# Skill の削除は全バージョンを削除する
# (SDK 1.2.0 以降は client.beta.skills.delete() も同じ動作)
client.skills.delete(skill_id="skill_01AbCdEfGhIjKlMnOpQrStUv")

🎯 ユースケース

👤 自身の開発・スクリプトに個人キー

開発者は、自身のツールやスクリプトに個人キーを使用することで、本人のロールと権限で動作し、組織を離れた際にはキーが自動的に無効化されます。キーの所有者と利用者の対応関係が明確になります。

🤖 CI / 本番サービスにサービスアカウントキー

CI や本番サービスなどの共有・自動化ワークロードには、特定の個人に依存しないサービスアカウントキーを使用します。担当者の退職によるキーの失効リスクを避けつつ、アイデンティティ単位での追跡が可能です。

📦 SDK 更新による Files / Skills API の GA 移行

SDK ユーザーは、対象バージョン以降に更新することで beta と GA の二重管理が解消され、一貫した型とページネーション (page / next_page カーソルや自動ページネーションヘルパー) で実装できます。

🔌 開発者への影響

👥 対象となる開発者

  • client.beta.files / client.beta.skills を使用している SDK ユーザー (Python、TypeScript、Go、Java、Ruby、C#)
  • beta レスポンス型 (BetaSkill など) に依存しているコードベース
  • ワークスペース API キーで運用している組織の管理者・開発者
  • CI / 本番サービスなどの共有・自動化ワークロードを運用するチーム

🛠️ 必要なアクション

  1. SDK 更新時の影響確認: 対象バージョン以降ではレスポンスが GA 形式に変わる。beta 形式の型 (has_more / first_id / last_id や BetaSkill 型) に依存している場合は、移行完了まで以前のリリースに留まるか、コードを修正する
  2. client.beta.skills.delete() の動作変更に注意: Skill を全バージョンごと削除するようになったため、特定バージョンのみ削除する意図のコードは見直しが必要
  3. キー戦略の見直し: 自身の開発・スクリプトには個人キー、CI や本番サービスにはサービスアカウントキーを使用し、新規統合ではアイデンティティ紐付きキーを優先する
  4. マルチワークスペースキーのヘッダー対応: ワークスペースにスコープしないキーでは anthropic-workspace-id ヘッダーを各リクエストに付与する

🧳 Files API の移行手順

移行は任意です。beta ヘッダーを送信し続ける限り従来形式を維持します。

  1. beta ヘッダー anthropic-beta: files-api-2025-04-14 をリクエストから削除する。SDK では client.beta.files の代わりに client.files を呼び出す
  2. ページネーションを after_id / before_id ループから page / next_page カーソル、または SDK の自動ページネーションヘルパーに置き換える
  3. expires_at フィールドを読み取る (null は有効期限なしを意味する)

🔄 ワークスペースキーの置き換え手順

  1. キーの種類を決める (自身のツールは個人キー、共有・無人ワークロードはサービスアカウントキー)
  2. 必要に応じて組織管理者がサービスアカウントを作成し、対象ワークスペースに追加する
  3. 新しいキーを作成する (複数ワークスペースが不要なら統合先ワークスペースにスコープする)
  4. ANTHROPIC_API_KEY 環境変数やシークレットマネージャーのエントリを新しいキーに置き換える
  5. リクエストの成功を確認してから、古いワークスペースキーを削除する

📝 まとめ

今回のリリースは、Files / Skills API の GA 化の総仕上げと、API キー管理のモダナイゼーションという 2 つの流れを示しています。SDK の beta 名前空間が GA 形式に統一されたことで beta と GA の二重管理が解消され、開発者は一貫した型とページネーションで実装できるようになりました。

  • 6 言語 SDK で client.beta.files / client.beta.skills が GA 形式のレスポンスに統一
  • beta ヘッダーを明示的に送信すれば従来形式が維持されるため、既存統合への影響は限定的
  • 個人キー / サービスアカウントキーの導入で「キーが所有者より長生きしない」セキュリティ原則を実現
  • 組織管理者はアカウント単位で使用状況を追跡でき、退職者のキーが残り続けるリスクも解消
  • ワークスペースキーはレガシーオプションとして引き続きサポート

新規統合ではアイデンティティ紐付きキー、あるいはさらに進んで Workload Identity Federation の採用を検討することが推奨されます。
