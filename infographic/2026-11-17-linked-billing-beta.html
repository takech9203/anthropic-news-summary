Claude API

Linked billing をベータ提供開始 - 顧客の Claude 組織によるアプリ API 使用料の支払いが可能に

📅 2026-11-17 | ソース: Claude Developer Platform Release Notes

概要

🔗

顧客の Claude 組織を OAuth でリンク

ベータヘッダー user-profiles-billing-2026-10-01 を使用すると、アプリの顧客が自身の Claude 組織を OAuth でリンクし、アプリ内での Claude API 使用料を顧客自身の組織に課金できる。リンク (API 上は connection) は顧客ごとに 1 回行えば継続する。

💳

リクエスト単位で支払者を選択

/v1/messages または /v1/chat/completions の各リクエストで billing_policy を設定し、「顧客払い」か「自社払い」かをリクエスト単位で選択できる。省略時は従来どおり自社払い。

💰

顧客は支出上限とリンク解除を自律管理

顧客は Claude Console からアプリに対する月次支出上限 (spend cap) の設定やリンク解除をいつでも実行できる。リンクは承認した個人ではなく組織に帰属するため、承認者が退職しても接続は維持される。

🛡️

課金不能時はアプリ提供者を保護

顧客に課金できないリクエストは、アプリ提供者に課金されるのではなく API 側で拒否される (403 / 402 エラー)。予期しないコスト負担を防げる。

🧪

ベータ提供

本機能はベータ提供であり、エンドポイント、パラメータ、挙動はベータ期間中に変更される可能性がある。本番導入にあたっては仕様変更の可能性を考慮する。

Before / After: API コスト転嫁の仕組み

Before: 従来

  • 💸 顧客の利用分も含め、すべての API 使用料をアプリ提供者が負担
  • 🧮 顧客への請求や従量課金の精算の仕組みを独自に構築する必要
  • ⚙️ コスト転嫁や精算にかかる運用負担が大きい

After: Linked billing (ベータ)

  • 🔗 顧客が OAuth で自身の Claude 組織をリンク
  • 💳 billing_policy で顧客組織に直接課金 (リクエスト単位で選択可能)
  • 💰 顧客自身が Claude Console で支出上限とリンク解除を管理
  • 🛡️ 課金不能時は API 側で拒否され、アプリ提供者に課金されない

主な変更点

🔗 組織の課金リンク

顧客が OAuth フローで自身の Claude 組織をアプリにリンクすると、以降のリクエストを顧客組織に課金可能になる。リンクは顧客ごとに 1 回行えば継続する。

💳 billing_policy パラメータの追加

/v1/messages と /v1/chat/completions のリクエストボディで支払者を選択できる。bill_to: "user_profile" で顧客払い、"self" または省略で自社払い。

💰 顧客側の管理機能

顧客は Claude Console で月次支出上限の設定やアプリのリンク解除を実行できる。承認には顧客組織の Admin または Billing ロールが必要。

🛡️ 課金不能時の保護

顧客に課金できないリクエストは、アプリ提供者に課金されるのではなく API 側で拒否される (403 / 402 エラー)。

⚠️ 実行環境はアプリ提供者側

レート制限、モデルアクセス、サービスティア、データ保持、暗号鍵はアプリ提供者側の設定が適用される。顧客側の ZDR / BAA / CMEK は適用されない。

顧客リンクの OAuth フロー

sequenceDiagram
    participant C as 👤 顧客 Admin
    participant A as 🛠️ アプリバックエンド
    participant O as 🔐 auth.claude.com
    participant P as 🔌 Claude API

    A->>P: POST /v1/user_profiles
    P-->>A: user profile ID
    A->>O: PAR リクエスト PKCE 付き
    O-->>A: request_uri 有効期間 600 秒
    A->>C: 承認ページへリダイレクト
    C->>O: 組織選択 + 支出上限設定 + 承認
    O-->>A: コールバック 認可コード
    A->>O: トークンエンドポイントでコード交換
    O-->>A: connection_id + アクセストークン
    A->>P: billing_policy 付きリクエスト
    P-->>A: レスポンス 顧客組織に課金

billing_policy の指定方法と必要なヘッダー

bill_to の値 支払者
user_profile リンクされた顧客の Claude 組織
self アプリ提供者の組織 (省略時のデフォルト)
ヘッダー 用途
anthropic-user-profile-id リンク顧客向けのすべての呼び出しで必須。対象の user profile ID (例: uprof_01HV9Z) を指定
anthropic-beta: user-profiles-billing-2026-10-01 billing_policy を設定する場合に必須

エンドポイントごとの対応状況

エンドポイント 対応
/v1/messages ✅ 対応。ただし bill_to: "user_profile" では課金型コード実行機能は使用不可 (400 エラー)
/v1/chat/completions ✅ 対応
/v1/messages/count_tokens ➖ billing_policy を受け付けるが課金には影響しない
/v1/messages/batches ❌ 顧客課金は非対応。bill_to: "user_profile" を含む個別リクエストはエラーになる

利用条件と制約

  • 🏢対象顧客は Anthropic に API 使用料を直接支払っている Claude Platform 組織のみ。AWS / Google Cloud / Azure のマーケットプレイス経由の組織や、Claude サブスクリプションプランのみの組織は 403 user_profile_not_billable で拒否される
  • ⚙️リクエストはアプリ提供者の組織内で実行されるため、レート制限、モデルアクセス、サービスティア、データ保持、暗号鍵はアプリ提供者側の設定が適用される。顧客側の ZDR / BAA / CMEK は適用されないため、HIPAA / FERPA / CMEK が必要な顧客はリンクすべきではない
  • 💳Max / Ultra / Team プランの月次 API クレジットや、パートナー / スタートアップ・プログラムのクレジットは支払いに使用できない。支払い不能時は 402 エラーで拒否される (クレジット不足と支出上限のどちらが原因かは応答から区別できない)
  • ⚖️bill_to: "user_profile" は顧客が指示した使用にのみ設定すべき。テストや評価、他顧客向けの作業に顧客課金を設定してはならない

セットアップの流れ

初回のみ、Claude Console で OAuth アプリを作成し (「Bill and link to organizations」を選択)、private_key_jwt 方式のクライアント認証と operator service account を設定する。クライアントシークレットは発行されず、Workload Identity Federation によるサービスアカウント認証を使用する。顧客ごとのリンクは以下の流れで行う。

1

user profile の作成

/v1/user_profiles で顧客用の user profile を作成し、返却された ID を保存する。

2

PAR の送信

PAR (Pushed Authorization Request) を https://auth.claude.com/v1/oauth/par に送信する (scope は billing:attribution、PKCE 必須)。

3

承認ページへリダイレクト

顧客を承認ページへリダイレクトする。承認には顧客組織の Admin または Billing ロールが必要。

4

顧客による承認

顧客が組織を選択し、月次支出上限を設定して「Link and authorize」を承認する。

5

コード交換

コールバックで認可コードを受け取り、トークンエンドポイントで connection_id とアクセストークンに交換する。

リンク解除

顧客組織またはアプリ提供者組織の管理者がいつでも解除できる。Console の User profiles ページのほか、revocation エンドポイント (https://auth.claude.com/v1/oauth/revoke) に connection_id を送信してバックエンドから解除することも可能。解除後は同じ user profile を再リンクできる。

💡 リンクは承認した個人ではなく組織に帰属するため、承認者が退職しても接続は維持される。

コードサンプル

Python Python SDK - 顧客払いリクエスト 
import anthropic

BILLING_BETA = "user-profiles-billing-2026-10-01"

client = anthropic.Anthropic()

response = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Hello, Claude"}],
    betas=[BILLING_BETA],
    extra_headers={"anthropic-user-profile-id": "uprof_01HV9Z"},
    extra_body={
        "billing_policy": {"type": "billing_policy", "bill_to": "user_profile"}
    },
)
Bash curl - 顧客払いリクエスト 
curl https://api.anthropic.com/v1/messages \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "anthropic-version: 2026-10-21" \
  -H "anthropic-beta: user-profiles-billing-2026-10-01" \
  -H "anthropic-user-profile-id: uprof_01HV9Z" \
  -H "content-type: application/json" \
  -d '{
    "model": "claude-sonnet-5-5",
    "max_tokens": 1024,
    "messages": [{"role": "user", "content": "Hello, Claude"}],
    "billing_policy": {"type": "billing_policy", "bill_to": "user_profile"}
  }'

主なエラーと対処

エラー 意味
403 user_profile_not_billable 顧客が課金不適格 (マーケットプレイス経由課金、サブスクリプションのみの組織など)
402 クレジット不足または支出上限到達 (応答からは区別不可)
400 顧客課金リクエストでの課金型コード実行機能の使用など
401 authentication_error トークンの失効・置換、または接続の終了

開発者への影響と必要なアクション

対象: Claude API を組み込んだ SaaS / アプリケーションを提供し API コストを顧客に転嫁したい事業者、顧客ごとの従量課金の精算を独自に構築している開発者、顧客側では Anthropic に直接支払いを行う Claude Platform 組織の管理者。既存の API 呼び出しに影響はなく、billing_policy を省略した場合は従来どおり自社払いでベータヘッダーも不要。

1

ベータヘッダーの追加

billing_policy を設定するリクエストには anthropic-beta: user-profiles-billing-2026-10-01 ヘッダーが必要。

2

OAuth アプリのセットアップ

Claude Console で OAuth アプリを作成し、operator service account と private_key_jwt 方式のクライアント認証を設定する。

3

user profile 運用の設計

顧客組織と user profile は 1 対 1 で接続される。顧客ごとに profile ID を保存し、顧客払いリクエストに必ず正しい ID を設定する。誤った profile ID を設定すると別の顧客組織に課金され、エラーは発生しない。

4

エラーハンドリングの実装

402 / 403 エラーを適切に処理し、顧客への案内 (クレジット追加、支出上限の見直し、再リンクなど) に接続する。

5

コンプライアンス要件の確認

リクエストはアプリ提供者の組織設定で実行されるため、ZDR / BAA / CMEK が必要な顧客にはリンクを案内しない。

ユースケース

🏢 SaaS / アプリの API コスト転嫁

Claude API を組み込んだ SaaS やアプリケーションで、独自の請求システムを構築することなく、顧客の利用分を顧客の Claude 組織に直接課金できる。従量課金の精算にかかる運用負担を軽減できる。

🤖 エージェント製品の従量課金精算

エージェント製品やプラットフォームで、顧客ごとの従量課金を精算する仕組みを独自に構築していた開発者は、billing_policy によるリクエスト単位の支払者選択に置き換えられる。顧客が指示した使用にのみ顧客課金を設定する。

💰 顧客側のコストガバナンス

顧客組織の管理者は、アプリごとに月次支出上限を設定し、不要になったアプリのリンクを Claude Console からいつでも解除できる。上限超過時は 402 エラーで拒否されるため、予算超過を防げる。

まとめ

Linked billing のベータ提供により、アプリの顧客が自身の Claude 組織を OAuth でリンクし、アプリ内の API 使用料を顧客組織に直接課金できるようになった。アプリ提供者は /v1/messages や /v1/chat/completions のリクエストごとに billing_policy で支払者を選択でき、顧客は Claude Console から支出上限の設定やリンク解除を自律的に管理できる。API コストの転嫁を独自の請求システムなしで実現できる一方、リクエストはアプリ提供者の組織設定で実行される点や、マーケットプレイス経由の組織は対象外である点など、導入前に確認すべき制約もある。ベータ機能のため、本番導入にあたっては仕様変更の可能性を考慮する必要がある。
