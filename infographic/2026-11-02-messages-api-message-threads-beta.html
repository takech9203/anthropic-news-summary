Claude API

Messages API にメッセージスレッド機能がベータ提供開始

📅 2026-11-02 | ソース: Claude API Release Notes

会話をサーバー側で短期間保持し、2 回目以降は新しいメッセージのみを送信。長い会話やエージェントループのリクエストサイズとレイテンシを削減

anthropic-beta: message-threads-2026-08-12

概要

🧵

会話をサーバー側で短期間保持

メッセージスレッドを使用すると、API が会話をサーバー側で保持するため、2 回目以降のリクエストでは新しいメッセージのみを送信すればよくなる。

⚡

リクエストサイズ削減と TTFT の短縮・安定化

長い会話やエージェントループでリクエストサイズが小さくなり、検証やトークン化の大部分が新しいターンのみを対象とするため、最初のトークンまでの時間 (time to first token) が短縮・安定化される。

🔧

導入は thread パラメータ 1 つだけ

リクエストに thread フィールドを 1 つ追加するだけで利用でき、レスポンスは通常のメッセージ形式のまま変わらない。料金やレート制限の変更もない。

🌐

マルチプラットフォーム対応

Claude API に加え、Claude Platform on AWS、Google Cloud 上の Claude モデル (Anthropic 管理)、Microsoft Foundry でも利用できる。

🛡️

ベストエフォートのため会話のコピー保持が前提

スレッドの保存は保証されない。アプリケーション側で会話全体を保持し、404 エラー時に create リクエストで再送するリプレイ処理の実装が前提となる。

Before / After: スレッドなし vs スレッドあり

Before (ステートレス)

  • 毎ターン会話履歴全体を送信する必要がある
  • 会話が長くなるほどリクエストサイズが増大
  • 検証とトークン化が会話全体に対して毎回実行される
  • 最初のトークンまでの時間が徐々に悪化
  • 多数のツール呼び出しを繰り返す長時間のエージェントループで影響が顕著

After (メッセージスレッド)

  • 2 回目以降は新しいメッセージのみを送信
  • リクエストサイズが小さくなる
  • 検証やトークン化の大部分が新しいターンのみを対象
  • 最初のトークンまでの時間が短縮・安定化
  • 料金とレート制限は変更なし

主な変更点

➕ thread パラメータの追加

Messages API リクエストに thread フィールドを 1 つ追加するだけで利用できる。レスポンスは通常のメッセージ形式のまま変わらない。

🆕 スレッドの作成 (create)

初回リクエストで会話全体、system、tools を送信し、{"type": "create"} を追加する。API は Claude の応答を含む会話をレスポンスの id に紐付けて保存する。

▶️ スレッドの継続 (continue)

2 回目以降は新しいメッセージのみを送信し、{"type": "continue", "previous_message_id": ...} を追加する。system と tools は省略する (スレッドが create リクエストの値を保持する)。

⏳ 有効期限

スレッドは最後のリクエストから 5 分で期限切れとなり、最後の使用から最大 1 時間以内に削除される。

🔁 リプレイ (再送)

スレッドはベストエフォートであり、継続できない場合は 404 エラー (thread_not_found) が返る。その際はアプリケーション側が保持する会話全体を新しい create リクエストで再送信する。

🧰 SDK スレッドヘルパー

Python、TypeScript、C#、Go、Java、PHP、Ruby の各 SDK にスレッドヘルパーが用意されており、ベータヘッダーの付与、create / continue の切り替え、404 エラー時のリプレイを自動で処理する。

数字で見るデータ保持ポリシー

5 分
最後のリクエストからの有効期限
1 時間
最後の使用からの最大削除期限
最大 4 個
thread 利用時の cache_control ブレークポイント
0 円
追加料金なし・レート制限の変更なし
データ保持の仕組み: スレッドの内容 (会話、システムプロンプト、ツール) はメモリ上に保持され、サーバー管理キーで暗号化される。永続ストレージには書き込まれず、最後の使用から最大 1 時間以内に削除される。ZDR (ゼロデータ保持) の対象外だが、他の ZDR 対象機能の利用には影響しない。

技術詳細

📋 リクエストフィールドの扱い (3 グループ)

グループ フィールド ルール
create 専用 system、tools create リクエストでのみ送信する。continue リクエストに含めると 400 エラー
固定 model、tool_choice、thinking、context_management、output_config、トップレベル cache_control、anthropic-beta 値のセットなど 毎リクエストで create 時と同じ値を送信する。異なる値は 400 エラー (thread_fingerprint_mismatch)
自由 max_tokens、stop_sequences、stream、metadata、service_tier など ターンごとに変更可能

💾 プロンプトキャッシュとの関係

スレッドは自動でプロンプトをキャッシュしない。プロンプトキャッシュは従来どおり cache_control ブレークポイントで制御する。毎ターンキャッシュするには、トップレベル cache_control をスレッドの全リクエストで送信する。thread 付きリクエストで指定できる cache_control ブレークポイントは最大 4 個となる。

🚨 エラー処理

ステータス error_code 意味
404 thread_not_found スレッドを継続できない。会話全体を新しい create リクエストで再送する
400 thread_fingerprint_mismatch 固定フィールドの値が create 時と異なる
400 thread_already_continued 各レスポンス id は 1 回しか継続できない
400 thread_continue_in_flight 同じ id からの別の continue リクエストが実行中
400 thread_unsupported_request スレッドが対応していない機能や組織設定を使用している

🚫 サポートされない機能

Message Batches、トークンカウント、コンパクション (compaction on demand)、コンテキスト編集 (一部を除く)、HIPAA readiness 有効組織、Inference hooks 有効組織では利用できない。また、スレッドの一覧取得・読み取り・削除用の API は提供されない。

💰 料金とレート制限

スレッドの利用による料金やレート制限の変更はない。

アーキテクチャ: スレッドのライフサイクル

sequenceDiagram
    participant C as 👤 クライアント
    participant A as 🔌 Messages API
    participant S as 🗄️ スレッドストア
    participant M as 🤖 Claude モデル

    Note over C,A: ターン 1 - thread type create
    C->>A: 会話全体 + system + tools
    A->>M: 会話全体を処理
    M-->>A: 応答
    A->>S: 会話 + 応答を id に紐付けて保存
    A-->>C: 応答 msg_001

    Note over C,A: ターン 2 - thread type continue
    C->>A: 新しいメッセージのみ + previous_message_id msg_001
    A->>S: 保存済みの会話を取得して再構築
    A->>M: 再構築した会話を処理
    M-->>A: 応答
    A->>S: 更新した会話を保存
    A-->>C: 応答 msg_002

    Note over S: 最終リクエストから 5 分で期限切れ
最大 1 時間以内に削除

    Note over C,A: 期限切れ後の continue
    C->>A: continue リクエスト
    A-->>C: 404 thread_not_found
    C->>A: 会話全体を新しい create リクエストで再送
    A-->>C: 応答 msg_003 で継続

コードサンプル

Python スレッドの作成と継続 
import anthropic

client = anthropic.Anthropic()

# ターン 1: 会話全体を送信してスレッドを作成する
first = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    cache_control={"type": "ephemeral"},
    system="You are a support agent for Acme. Keep replies short.",
    messages=[{"role": "user", "content": "Hi! I have a question about an order."}],
    thread={"type": "create"},
    betas=["message-threads-2026-08-12"],
)

# ターン 2: 新しいメッセージと前回レスポンスの id のみを送信する
# system と tools は省略する (スレッドが保持している)
second = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    cache_control={"type": "ephemeral"},
    messages=[
        {"role": "user", "content": "How long does standard shipping usually take?"}
    ],
    thread={"type": "continue", "previous_message_id": first.id},
    betas=["message-threads-2026-08-12"],
)

for block in second.content:
    if block.type == "text":
        print(block.text)

開発者への影響

🎯 対象となる開発者

💬

Messages API で長い会話やマルチターンのエージェントループを実装している開発者

🤖

ツール呼び出しを多数繰り返すエージェントアプリケーションの開発者

📉

最初のトークンまでの時間 (レイテンシ) やリクエストサイズの削減を求める開発者

✅ 必要なアクション

1

全リクエストにベータヘッダー message-threads-2026-08-12 を付与する (SDK ヘルパー利用時は自動付与)

2

初回リクエストに "thread": {"type": "create"} を追加する

3

以降のリクエストでは新しいメッセージのみを送信し、"thread": {"type": "continue", "previous_message_id": ...} を指定する

4

アプリケーション側で会話全体のコピーを必ず保持し、404 エラー (thread_not_found) 時に create リクエストで再送するリプレイ処理を最初から実装する

5

毎ターンのキャッシュが必要な場合は、トップレベル cache_control を全リクエストで送信する

🔄 移行ガイド

既存のステートレスな実装はそのまま動作するため、移行は必須ではない。スレッドを導入する場合でも、アプリケーションが会話の信頼できる情報源 (source of truth) であり続ける点に注意が必要である。スレッドの保存は保証されないため、会話のコピーを手元で管理し続ける設計を維持する。SDK のスレッドヘルパーや beta ツールランナー (デフォルトでスレッドを使用) を利用すると、リプレイ処理などを自動化できる。

ユースケース

🤖 長時間稼働するエージェントループ

多数のツール呼び出しを繰り返す長時間のエージェントループでは、従来は会話が長くなるほど TTFT が悪化していた。スレッドを使うことで新しいターンのみが処理対象となり、レイテンシが短縮・安定化される。

💬 マルチターンのチャットアプリケーション

カスタマーサポートのような連続した会話では、2 回目以降のリクエストで新しいメッセージのみを送信すればよく、リクエストサイズを大幅に削減できる。system と tools はスレッドが保持する。

🧰 SDK ヘルパーによる自動化

Python、TypeScript、C#、Go、Java、PHP、Ruby の SDK スレッドヘルパーや beta ツールランナーを使えば、ベータヘッダーの付与、create / continue の切り替え、404 エラー時のリプレイを自動で処理できる。

まとめ

メッセージスレッドは、長い会話やエージェントループにおけるリクエストサイズとレイテンシの課題に対する実用的な解決策である。thread パラメータを 1 つ追加するだけで導入でき、料金やレート制限の変更もない。一方で、スレッドの保存はベストエフォートであり有効期限も 5 分と短いため、アプリケーション側で会話のコピーを保持し、リプレイ処理を実装することが前提となる。SDK のスレッドヘルパーを利用すれば、これらの処理の多くを自動化できる。長時間稼働するエージェントを構築する開発者にとって、導入を検討する価値の高い機能である。
